# SmartRewrite

SmartRewrite 用来把已经写好的中文文章，重新组织成适合播客、旁白、人工朗读和 TTS 的口播稿。

文章和口播是两种不同的媒介。文章允许读者停下来、回看、跳读标题，也能依赖段落和排版理解结构；口播只能沿时间向前。听众听到一句话时，如果理解它所需的前提还没出现，或者指代需要回头确认，理解就会中断。

SmartRewrite 的工作不是给文章逐句添加口语词，也不是围绕原主题重新创作。它先理解原文已经成立的观点、事实、判断和逻辑关系，再按照听觉理解的顺序重新组织，并用自然说话的方式重新表达。

## article-to-spoken-script

`article-to-spoken-script` 是仓库中的文章转口播 Skill。

完整规则见 [`article-to-spoken-script/SKILL.md`](./article-to-spoken-script/SKILL.md)。

核心原则：

> 内容和论证保持成立，顺序和表达可以重建。

一次转写主要处理四件事：

1. **Semantic Reconstruction**：理解原文的事实、观点、判断、逻辑关系、概念边界和作者态度。
2. **Listening-first Reordering**：根据听觉理解的依赖关系重新安排原文已有内容。
3. **Spoken Reconstruction**：重新组织说话过程和口语句法，让表达自然、连续、信息紧凑。
4. **Audio Delivery**：处理指代、句长、数字、英文、标点和 TTS 朗读问题。

## 执行流程

Skill 按固定顺序执行：

`Understand → Reorder → Reconstruct → Speak → Review → Deliver`

先理解原文语义，再处理听觉顺序；前两步完成以后才生成完整口播 draft。之后单独进行口语句法处理、双向语义审查和最终朗读适配。

这里约束的是执行顺序，不是具体写法。不同文章可以有完全不同的重排方式、句子长度、聊天密度和表达节奏，只要作者原有的内容与论证仍然成立。

## 转写重点

### 原文语义

SmartRewrite 保护的不只是文章提到了哪些内容，也包括这些内容之间的关系。

两个观点即使都保留下来，如果原文的因果、前提、条件、判断方向或作者态度被改掉，仍然属于失真。

### 听觉顺序

当前判断需要的前提，应尽量在判断之前出现。

必要时可以前置解释、合并分散推理、移动案例、拆分复杂段落、明确指代或删除重排后的重复。

### 说话过程

口播需要像一个人在向另一个人解释事情。

反问、转折、自我回应、强调、总结等表达动作只有在原文存在相应思考过程时才需要出现。SmartRewrite 不为了制造“聊天感”替作者增加新的认知动作。

### 口语句法

句子可以重新写。

可以拆长句、调整语序、省略已经明确的主语、使用更自然的动作表达，也可以重新安排气口。

这些改变服务于理解和朗读，不改变作者原有的判断和逻辑。

### 作者声音

需要保留的是原文真实存在的判断强度、不确定性、讽刺、克制、态度和思考节奏。

SmartRewrite 不把作者统一改造成主持人、讲师或标准 AI 播客文风。

## 审查

成稿会从两个方向检查：

- **原文 → 口播**：重要内容、判断和逻辑关系是否丢失或改变。
- **口播 → 原文**：口播里新增的判断、关系和作者反应是否有原文依据。

同时检查表达是否被模型惯常的模板化过渡、重复总结、戏剧化对照或空洞铺垫污染。判断依据是这些表达是否服务原文，而不是维护一份固定词汇黑名单。

## 这一版为什么做减法

SmartRewrite 早期的一个问题，是每发现一种不理想的输出，就很容易再补一条规则。规则越来越具体以后，Skill 看起来更严密，模型真正执行时却需要同时记住大量互相重叠的限制。结果并不一定更稳定，反而容易把转写变成一种软性的规则匹配：模型忙着避免某些句式、补某些结构，却没有把注意力放在文章本身。

这一版选择把问题重新抽象回文章转口播最基本的矛盾：**文字的组织方式不适合直接搬进声音，但作者已经成立的思考不能在媒介转换中被改写。**

因此，Skill 不再试图穷举“什么不能写”，而是先固定一条认知流程。模型必须先理解文章，再决定听觉顺序，然后才开始重新说。口语句法、聊天感和 TTS 都放在后面处理，它们不能反过来决定作者原本说了什么。

这也是六阶段执行流程存在的原因。`Understand` 和 `Reorder` 把理解与写作拆开，避免模型边读边生成；`Reconstruct` 和 `Speak` 把内容重组与句法口语化拆开，避免“更像说话”变成重新创作；`Review` 再从原文和口播两个方向检查语义漂移；`Deliver` 只负责朗读与节目呈现。

### 不把忠实理解成保留原句

SmartRewrite 允许大幅调整原文顺序，也允许重新写句子。真正需要保持的是事实、观点、判断、概念边界以及它们之间的因果、前提、条件、对比和递进关系。

如果只是保留原句，文章仍然可能不适合听；如果只保留几个关键词，却改掉了这些关键词之间的关系，同样不算忠实。

所以这一版把“语义结构”放在原句之前。句子可以变化，作者为什么得出这个判断不能被改掉。

### 不把 AI slop 当成词汇问题

模型常见的空洞转折、戏剧化对照、自问自答、重复总结和所谓“金句”，很多时候并不是因为某几个词本身有问题，而是模型替作者做了原文里不存在的思维动作。

同一句“真正的问题是……”在一篇文章里可能完全合理，在另一篇文章里也可能是模型凭空制造的反转。维护句式黑名单只能让模型换一种方式继续生成同样的东西。

SmartRewrite 因此检查的是 **discourse move 是否有来源**。反问、转折、强调、总结、修正这些说话动作可以存在，但应该来自原文真实的冲突、态度、判断变化或推理节点，而不是为了让口播显得更像口播。

### 少规则不等于少步骤

减法并不是把 Skill 重新缩成一句“请忠实改写”。

转写质量曾经不稳定，一个重要原因就是缺少明确的执行步骤。只有原则，没有过程，模型很容易直接跳到写作，再用后面的规则给已经生成的文本做修饰。

这一版减少的是重复约束和局部禁令，保留并强化的是过程约束。六个阶段必须按顺序发生，但每个阶段内部仍然保留模型处理不同文章的自由度。

这是一种刻意的取舍：**少规定结果长什么样，多规定模型先做什么、后做什么。**

### 这一版仍然依赖模型判断

SmartRewrite 不是规则引擎。语义地图、听觉重排、说话过程和最终审查都仍然依赖模型对文章的理解。

因此，它的目标不是通过越来越多的限制让错误理论上“不可能发生”，而是让模型把能力用在正确的问题上，并让语义漂移更容易在生成流程中被发现。

后续迭代更适合通过不同类型文章的实际转写和回归测试判断是否存在全局性缺陷，而不是因为某一句坏输出就继续给 Skill 增加一条特殊规则。

## 使用方式

在支持 Skill 目录的环境中，直接使用 `article-to-spoken-script`。

```text
使用 article-to-spoken-script，将下面的文章重新组织成可以直接朗读的口播稿。
完整理解并保留原文观点、判断和逻辑关系，按照听觉理解顺序重排，用自然口语重新表达。
```

输入最好包含：

- 完整文章正文
- 用途，例如播客、视频旁白或 GPT-SoVITS
- 时长或字数限制，如有
- 必须保留、删除或调整的内容，如有
- 节目名称、讲述者名称或固定开场语，如需要

默认只输出标题和完整口播正文，不输出内部分析和检查过程。

## 目录结构

```text
SmartRewrite/
├── README.md
└── article-to-spoken-script/
    ├── SKILL.md
    ├── references/
    │   └── conversational-discourse.md
    └── agents/
        └── openai.yaml
```

`SKILL.md` 定义转写任务、执行顺序和验收边界。

`references/conversational-discourse.md` 提供听觉组织、说话动作和口语句法的参考机制。

`agents/openai.yaml` 提供 Skill 的展示信息和默认调用提示。

## 适用范围

适合：

- 公众号文章转播客文字稿
- 长文章转视频旁白
- 为 GPT-SoVITS 等 TTS 准备可直接朗读的文本
- 修正已有口播稿里的书面句法、信息跳跃和语义漂移
- 在保留作者思考的前提下，把文章重新组织成连续可听的表达

SmartRewrite 让已经成立的内容，在声音里继续成立。
